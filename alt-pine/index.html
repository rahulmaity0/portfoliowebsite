  1. Ledger & inventory Inventory-Management

    Jewellery Ledger & Inventory System

    The backend that runs the books of a working gold manufacturing business.

    Every issue and receipt updates both the locker inventory and the client's balance inside one @Transactional method, so the two can never drift out of sync. The trade's making charge is modelled as an effective-purity uplift: an issue bills the client at purity plus making charge, while the locker is debited only the metal that physically left — and the difference between those two numbers is the business margin. BigDecimal with explicit HALF_UP rounding throughout, and two rules the service checks instead of assuming: an issue can't exceed the gold in the locker, and a receipt can't exceed what the client owes. REST endpoints cover clients, per-client ledgers, a dashboard and a monthly JPA report, all behind stateless JWT auth. Built on a feature branch and merged via pull request.

    POST /api/transactions @Transactional locker + client balance invariant checks ledger & monthly report

  2. SDET banking-api-test-automation-framework

    Payments API Test Automation Framework

    I wrote both the API and the suite that tests it.

    A Spring Boot payments API handling transfers, merchant payments and account balances, paired with a layered REST Assured framework. The framework separates an API client, reusable request specifications, request models, a centralised test-data factory and a shared base class, so test classes contain assertions instead of HTTP plumbing. Coverage goes after the paths that actually cost money: idempotent duplicate payments, insufficient funds, and high-value payments flagged for fraud review. The suite runs against a real embedded server on a random port, publishing Allure reports from GitHub Actions on every push.

  3. Web service url-shortener

    URL Shortener Service

    Small enough to hold in your head, which is what makes the edge cases interesting.

    A REST API that shortens long URLs, redirects visitors with an HTTP 302 and a Location header, and tracks a click count per link. Codes are six collision-safe base62 characters — roughly 56 billion combinations — with each candidate checked against the database before use and retries capped, so a saturated keyspace fails fast instead of looping forever. Click counts increment through JPA dirty checking inside a transaction rather than an explicit save call, and incoming URLs are rejected by Bean Validation before they ever reach the service layer. Integration tests cover redirect behaviour, click counting, validation failures and unknown codes.

    POST /api/urls base62 code collision check 302 + Location click count
